# CartBack PRD v6：自然对话、方案草稿与可靠执行

> 日期：2026-10-06
> 状态：待书面评审的目标设计，本文不声明代码已经实现。
> 用户已认可的方向：减少对表达的硬限制；模型理解与表达，代码管理业务状态和执行。
> 范围：重写对话流程 B/C/D，同步记忆 A3、按钮 F1、降级 G2 与验收 H。批次、归因和数据隔离等其他功能沿用既有规则。

## 0. 文档关系与目标

本文以 `docs/prd-latest.md` 可读正文中的 A–I 工程口径为审查基线，同时参照 `PRD_CartBack_v5.md` 和记忆设计。原文件保留，用于追溯。文末 v5.1 引用的三张表格未在本地展开，不视为已经审查。

本文通过书面评审后，在上述范围内优先于旧版对应条款。旧版已经通过测试的业务保护不能因为流程迁移而撤掉。尚未替换的代码仍按现有行为运行；上线前必须列明新旧差异。

产品目标：商家可以自然表达需求、修改和撤销选择，快速看到可编辑的邮件方案，明确批准自己要执行的内容。理解错误可以被发现和纠正，未经批准的变更不能进入发送。

本轮不引入向量数据库、多代理、通用工作流平台，不重写 Next.js 前端，不重设计数据库，不删除未验证替代的 Python 实现。

### 0.1 保留的业务不变量

1. 商家数据按现有用户与店铺边界隔离；商家私话不进入消费者邮件。
2. 用户看见“已记录”的业务变更已保存；用户看见“已发送”的结果来自发送记录。
3. 批准对象与执行对象一致；内容、优惠、受众范围等关键变更使相关批准失效。
4. 折扣码来自店铺真实创建或校验结果，不能由模型生成字符串冒充真实码。
5. 退订、发送资格、频控、署名、时区等执行检查继续有效。
6. 重试不能重复创建同一逻辑发送；已发送记录只读，未发送部分才可修改。
7. 演示、预估和实际结果分别标注。

### 0.2 明确撤销的旧规则

| 旧规则 | 新规则 |
|---|---|
| 四槽 4/4 才能继续；满槽自动获得确认资格 | 每个动作分别计算准备条件；完整文本不等于可以发送 |
| filled_count 单调不减 | 允许修改、撤销、清空；计数仅兼容诊断，不控制流程 |
| 每槽最多追问一次，含糊或未回应后推断落定 | 可以保留未知、候选和待决定项；未回应不等于批准 |
| 指定轮数后强制补齐并收口 | 发现停滞时提供低成本出口，不替用户制造决定 |
| 固定 audience > reason > offer > goal 问序 | 优先回答用户本轮问题，再询问当前动作真正缺少的必要信息 |
| 每轮固定复述、提问、chips，限制为三句 | 保持自然相关；重要变更有可见摘要，格式和句数不决定业务正确性 |
| 含“改成”等词才算有效改口 | 模型识别具体修改、撤销和否定语义；代码应用明确变更 |
| S2 后冻结整个需求并靠例外解冻 | 草稿始终可编辑；批准版本不可变，新编辑形成新版本 |
| 确认活动参数即沉淀长期偏好 | 活动只沉淀历史；长期偏好需要明确长期意图 |
| AI 失败隐藏所有方案卡 | 按能力降级；已保存内容和确定性操作仍可用 |

## 1. 职责与处理流程

### 1.1 模型职责

模型负责理解本轮意图、提出信息变更、识别歧义、回答业务问题和撰写文案。它可以建议修改与默认方案，但不能宣布建议已经被用户批准。

模型不直接决定阶段、不直接写数据库、不创建优惠码、不调用发送执行器。其输出是受控的变更提案，不是执行授权。

### 1.2 代码职责

代码负责合并和保存变更、版本管理、动作资格、按钮生成、执行校验、幂等和结果记录。持久化数据是界面与执行的共同来源，不能以模型回复字符串反推成功状态。

### 1.3 每轮流程 B1–B5

| 环节 | 新定义 |
|---|---|
| B1 理解 | 接收用户原文、相关上下文和当前草稿，产出意图与变更提案 |
| B2 应用 | 校验结构、目标、作用域和来源；应用明确变更，保留未决候选 |
| B3 保存 | 保存消息、当前草稿和变更来源；关键业务变化增加草稿版本 |
| B4 决策 | 从保存后的状态计算可用动作及阻断原因，确定下一步是否需要询问 |
| B5 表达 | 基于保存结果回复；卡片、按钮和执行状态直接读代码结果 |

解释性回复可以使用模型。业务保存失败时，不发送“已改好/已记住”的成功表述；保留本轮原文供重试并提示未保存。模型表达失败但 B3 已成功时，使用简短确定性摘要，不撤销已经保存的正确变更。

理解与表达是两个逻辑阶段，不强制固定模型调用次数。可以复用提案中的措辞，但只有与提交结果一致的内容才可发布；不把合并前的回复当作权威。卡片不需要通过模型重新写一遍。

## 2. 业务信息 C：内容与决定分开

### 2.1 四类信息的用途

| 信息 | 用途 | 缺失时的处理 |
|---|---|---|
| 受众 audience | 选择真实收件人范围 | 可以写通用预览；准备发送时必须有能解析的范围 |
| 原因 reason | 调整劝购角度 | 保持未知，使用中性提醒，不推断“忘记结账” |
| 优惠 offer | 决定利益点与真实优惠资源 | 区分未决定与无优惠；需要优惠时要求具体参数 |
| 目标 goal | 复盘对照或优化方向 | 可选；没有量化目标不阻止预览或发送 |

“加购未付”是行为分组或筛选条件，不自动成为“流失原因”。用户没有给出原因时，不要求模型补一个原因满足计数。

### 2.2 值、来源与决议

来源至少区分：用户表达、用户批准的建议、店铺数据、明确长期偏好、指定活动历史、系统建议。

不能用一个 inferred 标记同时表达“用户含糊说过”“系统猜测”“默认值”和“历史复用”。系统建议可以展示，但不能覆盖已经确定的值，也不能被称为用户事实。

未提供的信息为空。优惠使用明确决议：`undecided`（未决定）、`none`（无优惠）或具体优惠配置。`待定`不作为真实优惠类型参与建码或发送。

候选与当前值分开存放。历史或偏好预填的信息在草稿上标来源；不自动升级为用户对本次发送的批准。

### 2.3 修改、撤销与否定

理解结果允许以下业务变更：

- `set`：补充或替换当前活动某项信息。
- `clear`：撤销该项决定，使其回到未知或未决定。
- `propose`：保存建议或待讨论的候选，不修改当前决定。
- `resolve`：接受、拒绝或暂缓已有候选。

“别用九折，先不放优惠”是设置无优惠；“优惠我重新想想”是清空优惠决定，两者不可混同。

“不改”“不要改”“还是原来那拨人”表达拒绝候选。明确否定不能通过关键词命中被改写为肯定。

明显的补充不必制造冲突。例如“还要排除已经购买的人”是在受众条件上追加排除，不应整体替换原受众。

### 2.4 歧义与冲突

只有存在实质不同的候选、且影响当前动作时才需要澄清。回复可说清旧值与新候选，不以重复追问次数自动决定结果。

用户不回答、说“以后再说”或转聊其他问题时，保留现值与未决候选。允许继续聊天、查询和预览；执行所需的歧义未解决时，准备或发送动作说明缺少什么。

不同字段的多个候选独立保留。解决一个不能删除另一个。相同字段的新候选取代旧候选时，需要保留来源供追溯。

用户明确修改当前活动时，不要求必须出现固定修正词。不确定是咨询还是修改时，将内容作为候选或询问，而不是静默执行。

### 2.5 对话停滞与“别问了”

模型可以根据当前上下文决定最有价值的问题。一轮优先问一个关键问题是体验建议，不是要求每条回复带问号的验证规则。

用户要求停止追问时：

1. 停止连续采集，保存本轮已经明确的信息。
2. 能写预览则提供带未定项标记的预览；不能生成则说明当前能力并保留进度。
3. 解释发送前仍需确认的必要项目，不自动补受众、折扣或目标。
4. 高折扣提示和执行硬约束仍有效，但不为了提示而丢掉用户输入。

可记录停滞轮数用于观测或调整问法，不能把计数用作用户决策的替代。导览、查询和功能介绍不消耗业务采集预算。

## 3. 方案与执行 D：草稿可变，批准不可变

### 3.1 按动作判断准备条件

| 动作 | 必要条件 | 不要求 |
|---|---|---|
| 写邮件预览 | 有邮件营销意图或用户明确要求写邮件；生成能力可用，或可使用用户选定的模板 | 四类信息填满、真实优惠码、量化目标 |
| 准备发送方案 | 受众可解析；优惠已选择 none 或具体配置；邮件内容可生成或已存在 | 已实际发送、量化目标、推断出的流失原因 |
| 实际发送/预约 | 当前版本存在；用户批准具体动作与范围；资源准备和执行检查通过 | 模型成功措辞、某个聊天阶段名称 |
| 查询/编辑已保存内容 | 有权限访问对象，编辑目标明确 | 模型在线、重走采集 |
| 效果复盘 | 对应的真实发送与效果数据可用 | 用户事先设置量化目标 |

缺少条件时返回具体阻断原因，而不是统一“信息不完整”。部分受众歧义只有在可以确定不影响该动作时才允许预览；不能把模糊候选转成真实筛选条件。

### 3.2 草稿、预览与准备资源

预览是可编辑产物，允许提前创建、持久化和刷新恢复。预览不会生成发送批准，不会自动建券，不会自动发邮件。由用户发起预览与旧版 demo 自动跳步、自动建立执行产物明确区分。

未决定优惠时可以展示待确认区域，不把“待定”当成真实优惠写给消费者。内容尚有占位符或未证实产品卖点时，不能通过发送检查。

“准备发送方案”可以创建或校验真实优惠码，但这个动作需要明确表达其副作用。界面说明它会建券且不会发送。优惠码失败时保留草稿和失败原因，提供重试、选择现有码或无优惠方案；不把整张草稿隐藏。

未连接店铺时保留原优惠选择，说明其尚不可执行。用户选择改为无优惠才生成无优惠版本；不能静默删除折扣以获得发送资格。

### 3.3 版本与批准

每个草稿有稳定对象 ID 和业务版本。修改受众、优惠、内容、发送时段或其他会影响执行的字段产生新版本。仅新增聊天消息或查看页面不改变业务版本。

尚无草稿时，活动也有独立业务版本，用于约束首次预览、采集变更和候选动作。候选新增、替换或解决改变所属对象版本，使旧候选按钮失效。预览生成任务绑定其输入活动版本；结果返回时输入已经变化则不挂到当前对象上。

批准绑定：对象 ID、业务版本、动作类型、执行范围、发送时间和必要的风险确认。批准“生成草稿”不等于批准“创建优惠码”，也不等于批准“发送”。

批准后的快照不可原地修改。编辑产生新版本，相关发送批准失效，旧版本未发送的任务必须停止或转为等待重新批准。旧内容和已发送记录保留。

### 3.4 明确的动作入口

按钮由服务端可用动作生成，携带语义 ID、对象类型、对象 ID 和对象业务版本。首次预览及没有草稿的采集动作绑定活动；已有草稿的准备、编辑和发送动作绑定草稿；候选决议另带候选 ID 并绑定其所属对象版本。显示文字可修改，不能依赖“把按钮文字发送给模型再猜一次”执行动作。

动作示例：`preview_email`、`prepare_plan`、`send_now`、`schedule_send`、`retry_resource`、`accept_candidate`、`reject_candidate`。这些是业务协议，不要求前端展示内部 ID。

聊天中的“确认/就这样/发吧”只能在当前有唯一、已展示且未过期的待批准动作时绑定该动作。否则说明要确认哪个对象。不能根据关键词在任意上下文创建发送授权。

发送入口显示明确语义，例如“发送本版邮件”或“预约到周五 10 点”，同时展示对象、范围和版本对应的可见内容。不用含义不明的通用“确认”同时代表多个操作。

### 3.5 发送与检查

预检提供当前条件与修复指引，发送前再次验证真实资源、权限、批准版本和收件人资格。预检通过不代替最终检查。

批准时固定允许的受众范围；执行前退订、已购买或其他资格变化可以继续排除，不能静默增加新收件人。数量减少如实记录排除原因与实发数量。扩大范围、改变优惠或内容需要新版本及新批准。

发送执行器使用已批准的内容快照。变体、语种和模板展开遵循既有渲染规则；用户批准的是可查看的模板/变体规则及其业务参数，不是任意模型生成的新内容。不得绕过已批准快照临时重写。

发送任务以逻辑操作 ID 幂等。队列、预约、发送中、成功、部分失败和失败分别记录；不能将任务入队表达为已发送。保存批准、快照和任务提交需要可靠的一致性边界。

对已发送内容的修改不追溯生效。修改未发送部分时，等待正在提交的发送完成后明确剩余范围，再生成新版本和批准；不能承诺撤回已经进入供应商的邮件。

## 4. 记忆 A3：事实、偏好、活动历史

| 类型 | 示例 | 复用方式 |
|---|---|---|
| 稳定店铺事实 | 品牌、主营品类、主要市场 | 相关时作为背景；当前活动可以明确覆盖 |
| 明确长期偏好 | “以后默认不打折” | 作为可见默认，用户可修改、删除 |
| 活动历史 | 上次给加购未付客户九折 | 用户指定复用时复制到当前草稿，展示差异 |

每条可复用记忆至少有值、来源消息或外部数据来源、作用域、更新时间、确认状态。模型建议和语义未确认的提案留在候选区，不以“用户明确说过”形式进入长期资料。

一次活动的批准不会自动更新长期偏好。出现长期表述时保存对应偏好；与已有偏好矛盾时明确展示替换结果，只替换同一主题，保留无关限制。

“这次”类内容默认属于当前活动。明确长期与临时条款同句出现时，按各自语义分开处理；无法确定作用域时不写长期资料，可以询问。

记忆验证不要求所有语义必须逐字匹配。保存原话和出处，区分直接事实与模型归一化；对会改变受众、优惠成本或硬限制的归一化值，必须有可见的确认或确定性解析结果。模型 confidence 不代表用户批准。

用户可以查看已保存的长期资料，编辑和删除。删除后不能从旧摘要或历史聊天自动复活；历史活动保留为历史，不能继续充当被删除的默认偏好。

恢复活动保留业务草稿、候选、历史来源和有效版本；重置本次对话的追问/停滞计数。没有审批记录时不能根据历史消息中的“确认”重建发送批准。存在有效预约或已批准任务时按任务记录恢复，不从聊天阶段猜测。

长期记忆不能跨用户或未经授权的店铺复用。当前只有用户级资料时，不假设已经实现多店隔离；接入多店前必须补齐实际作用域。

## 5. 按钮、界面与建议 F

### 5.1 首屏与采集完成按钮

首屏欢迎及正在采集的状态不出现“好，帮我写一封 / 介绍一下其他功能 / 其他需求”这三个完成后按钮。保留用户已明确要求的显示时机。

三个按钮在完成当前活动的必要信息采集后出现。这里的“完成”定义为：受众可解析、优惠选择明确、没有影响准备方案的未决候选；原因与量化目标可以保持未知。不是四项文字非空。

没有信息也可以由用户主动输入“先写一个预览”，生成带未定项的预览。这不表示采集已完成，也不自动显示这三个按钮。导览在任意阶段可通过用户输入进入。

采集中的回答选项可以按需展示；它们与完成后的三个出口分开。无合适动作时不为了凑数量显示无用按钮。

### 5.2 运营建议与硬阻断

高折扣、推荐时段、文案风格是运营建议。先保存用户的提议到草稿，再展示来源与影响，不因提示丢弃当前输入。达到现有高折扣阈值时，最终发送批准需要明确覆盖风险提示；同一版本不重复让用户确认同一风险。

没有毛利或店铺历史时承认未知，不能编出“上次更好”的数字。建议更改优惠需要用户接受；点击建议产生新草稿版本。执行硬条件不能被“别问了”或风险确认覆盖。

### 5.3 恢复与状态

刷新后从同一持久状态恢复当前草稿、可用动作、资源失败和任务结果。不会只因为存在草稿就隐藏未完成的流程。

可以在现有聊天卡片与邮件页面落地；不增加流程画布。不要求以聊天气泡展示所有细节，关键变更和执行范围通过同源卡片可见。

## 6. 降级 G：按能力恢复

| 能力 | 模型不可用时 |
|---|---|
| 保存原文、查看状态、查询已有对象 | 保持可用 |
| 用户在现有编辑器明确修改字段 | 正常保存和校验 |
| 自由文本中的复杂需求理解 | 保存原文并标待处理，不猜测或强制填满 |
| 新文案生成、复杂分析 | 明示暂停；已有内容可继续编辑 |
| 用户选择既有模板生成预览 | 明示模板来源，不冒充新模型生成 |
| 发送已存在且被批准的完整版本 | 执行条件通过即可，不额外要求对话模型在线 |

失败原因不统一说成 Key 配置错误。区分未配置、认证失败、限流、超时和供应商异常，提供对应恢复路径。

恢复后处理待理解消息必须考虑当前版本：用户已经手动修改的字段不能被迟到的模型结果覆盖；旧版本生成任务的结果不挂到新版草稿上。

## 7. 数据与接口的渐进兼容

以下为目标契约，不要求一次性换掉现有存储和端点。

```ts
type AvailableAction = {
  id: string;
  kind: string;
  label: string;
  targetKind: 'act' | 'draft';
  targetId: string;
  targetVersion: number;
  candidateId?: string;
  enabled: boolean;
  blockedReasons: string[];
};

type TurnResult = {
  actId: string;
  draftId?: string;
  draftVersion?: number;
  appliedChanges: unknown[];
  pendingCandidates: unknown[];
  availableActions: AvailableAction[];
  reply: string;
};
```

业务版本和动作令牌由服务端生成，不能信任模型填写的版本或用户范围。HTTP 写入检查所属用户、对象版本和动作有效性。相同操作重复提交返回既有结果；过期动作返回明确版本冲突并刷新状态。

优先复用现有 `acts`、`drafts`、`jobs`、`agent_profile`、`execution_snapshot`。必要时增加业务版本、来源和批准元数据；不另建完整事件溯源平台。`updated_at` 继续用于时间记录，不作为长期的唯一业务版本。

`S0/S1/S2/S3` 和 `filled_count` 可暂时作为兼容字段输出，但不再决定发送资格。前端读取新动作契约后，不自行合成确认或发送按钮。旧文字 chips 在过渡阶段由服务端显式适配，不能让同一个按钮同时走两套执行路径。

历史 `待定` 优惠迁移为未决定；缺少来源的旧 inferred 值保留为待核实，不能自动转 explicit。旧 prefs 中来源不清的活动参数只作为历史提示，不恢复为长期默认。

未知协议版本必须明确拒绝，不能静默回落为旧四槽补齐。目标状态的文字指令只在单一动作上下文绑定操作；迁移中两条路径需有明确服务端版本选择。

## 8. 验收 H：业务不变量与语义回放

### 8.1 必须通过的业务场景

| 场景 | 必须观察到的结果 |
|---|---|
| 新用户首屏 | 没有三个完成后按钮 |
| 仅说“帮我写一封提醒邮件” | 可请求预览；不猜真实受众、不建券、不发送 |
| “原因不知道，目标也没想好” | 保持未知；不制造原因与目标，不因此反复追问 |
| 优惠是待定 | 可以预览，但准备发送需完成优惠选择 |
| “不放优惠” | 保存 none，跳过建码 |
| “优惠重新想想” | 清空决定；以前版本不能继续发送 |
| 冲突后“不改/不要改/还是原来的” | 保留旧值，关闭对应候选 |
| 冲突后换个话题 | 保留现值与候选；回答新问题，不推断用户同意 |
| 两项同时冲突，解决其中一项 | 另一项仍保留且可独立解决 |
| “别问了，品牌叫 Acme，给九折” | 保存明确品牌与优惠；停止采访；未定项不自动补齐 |
| “别问了，折扣给90%” | 保存提议，展示建议；未批准风险和发送前不执行 |
| 功能导览、多次查询 | 不修改活动参数，不触发强制补齐 |
| 旧活动恢复 | 保留业务记忆；没有继承耗尽的追问计数 |
| “这次推鞋子” | 不改变长期主营资料 |
| “以后不允许免邮” | 保存禁止免邮的偏好，不保存默认免邮 |
| 修改一项长期限制，另一项继续保留 | 只替换被纠正的主题 |
| 删除长期偏好后刷新并新建活动 | 不从旧摘要复活该偏好 |
| 生成预览后刷新 | 预览和未定项可恢复；没有发送批准 |
| 建券失败 | 草稿仍可见，重试与其他选择有明确动作 |
| 准备方案后只说“确认”，有多个对象 | 不猜对象、不发送 |
| 发送排队后修改内容或受众 | 旧任务停止/等待重新批准；不发送混合版本 |
| 发送期间重复点击、超时重试 | 同一逻辑操作不重复实发 |
| 发前新增退订 | 继续排除；说明实发与排除，不扩大批准范围 |
| 模型不可用，有完整批准版本 | 可按执行检查发送；状态由执行记录决定 |
| 模型迟到返回旧版本结果 | 不覆盖当前草稿 |
| 任务预约、排队、部分失败 | 分别显示对应状态，不统一显示“已发送” |

### 8.2 测试与评测分工

确定性测试验证合并、作用域、版本、批准、幂等和恢复规则；测试结构化提案不能冒充真实模型理解测试。

模型回放使用固定原始对话、否定、撤销、插话、同义表达和多轮修正，检查提案与最终业务结果。样本按用途分为迭代集和未用于提示词调优的评估集，记录模型和提示词版本。

不因换了措辞、超过三句或没有每轮问号而判业务失败。质量记录包括：错误修改数、错误长期记忆数、重复询问已明确信息数、预览和发送成功路径、纠错后的恢复能力、延迟与调用成本。

发布要求：相关确定性测试、后端构建、前端构建和类型检查通过。将旧测试分为执行不变量与旧产品行为：数据隔离、真实码、批准一致、幂等和发送资格等不变量断言必须保留；§0.2 已明确替代的四槽门槛、强制补齐、单调计数等行为断言可以按新需求重写，并逐项记录旧条款、新条款及替代验收案例。不能因为实现失败而删除仍然有效的断言。模型回放需要展示与当前基线的结果差异，执行不变量必须全部通过。

## 9. 迁移边界与下一阶段

实施顺序以书面实施计划为准，建议按以下边界拆分：

1. 先建立明确的变更与可用动作契约，给现有前端提供兼容适配。
2. 将草稿资格从四槽计数中分离，实现清空、候选与按动作阻断原因。
3. 统一预览、资源准备、版本批准和发送任务；保留现有真实发送检查。
4. 区分长期资料与活动历史，补齐来源与删除语义。
5. 替换对话提示词和固定话术护栏，按能力降级并运行模型评测。

每步可单独测试、回滚，迁移中不删除尚未验证的旧实现。服务端协议版本选定后，同一活动的动作不能由新旧两套流程同时处理。

本文没有把频控从当前实现值直接改成旧文档值，也没有改变 holdout、归因窗口或批次规则；这些差异继续单独管理，不随本次对话改造顺带修改。
