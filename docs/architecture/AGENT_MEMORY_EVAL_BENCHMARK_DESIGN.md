# CartBack Agent 记忆、Eval 与 Benchmark 渐进式设计

> 状态：设计稿，不代表已经实现  
> 版本：v1.0 · 2026-08-13  
> 适用范围：`backend/` 中的 IGDE Agent、上下文管理与服务端存储

## 1. 目标

本设计只解决三个问题：

1. Agent 在新建挽回任务时，能记住少量稳定的店铺信息，避免重复询问。
2. Agent 的对话、记忆与护栏质量可以被重复评测，而不是依靠人工感觉。
3. 每次修改模型、提示词或上下文策略后，可以量化质量、延迟和成本变化。

设计遵循渐进原则：先完成固定字段、确定性校验和小型数据集；验证产生真实价值后，再增加多店铺、检索和效果学习。

## 2. PRD 约束

记忆与评测必须服务于 CartBack 的产品主线：

- 用户通过自然聊天完成邮件挽回配置，前端不暴露表单式收集进度。
- 已明确的信息不能重复询问。
- 用户私下表达的吐槽和底牌不能进入客户可见邮件。
- 未确认前不得声称已经发送。
- 邮件语言跟随收件人 locale，不跟随商家聊天语言。
- 没有真实发送、订单与归因数据时，不得把演示或估算结果表达为真实效果。

因此，记忆不是完整聊天归档，也不是自由发挥的“用户画像”。它只是 Agent 可以安全复用的少量业务事实。

## 3. 当前基线

当前后端已经具备：

- `act.needs`：当前挽回任务的 audience、pain、goal、offer。
- `act.messages`：当前会话完整消息。
- `act.memory`：会话内的 `facts / decisions / corrections`。
- `context_summary`：长会话压缩结果。
- 基于 token 预算的上下文裁剪。
- `memory_patch` 原话证据校验。
- LLM 调用数、token、上下文压缩、记忆接受/拒绝等运行指标。
- `node:test` 自动化测试。

当前 `memory` 随 `act` 保存，新建任务会重新初始化，所以它属于会话记忆，不是跨任务长期记忆。

## 4. 总体演进

| 阶段 | 目的 | 记忆能力 | Eval | Benchmark |
|---|---|---|---|---|
| M0 基线 | 先知道现在怎么样 | 保持现状 | 固定小型样例集 | 记录质量、延迟、token 基线 |
| M1 MVP | 新任务少重复问 | 每用户一份固定字段资料 | 自动评测写入、召回、纠错、隔离 | 改造前后对比 |
| M2 增强 | 支持多店与可控管理 | `user + store` 作用域、字段编辑 | 扩充脱敏真实案例 | 持续回归与灰度门槛 |
| M3 学习 | 用真实结果改善策略 | 真实发送/归因效果记忆 | 离线策略评测与人工审核 | 质量、ROI、成本联合观察 |

M1 完成前不引入向量数据库、Embedding、复杂召回评分或自动经验归纳。

# 第一部分：记忆设计

## 5. M1 的最小记忆模型

M1 只增加一份跨任务的 `agent_profile`，按 `user_id` 隔离。当前任务状态和会话记忆保持不变。

```text
当前任务：act.needs
当前会话：messages + context_summary + act.memory
跨任务资料：agent_profile
```

### 5.1 固定字段

```json
{
  "product": "运动鞋",
  "market": "德国",
  "currency": "EUR",
  "brand_tone": "年轻直接",
  "default_offer": "8%折扣",
  "constraints": ["客户邮件不要出现中文", "不要强调运费贵"]
}
```

字段含义：

| 字段 | 用途 | 例子 |
|---|---|---|
| `product` | 稳定主营商品或品类 | 跑鞋 |
| `market` | 主要销售市场 | 德国 |
| `currency` | 默认金额币种 | EUR |
| `brand_tone` | 品牌长期表达风格 | 年轻直接 |
| `default_offer` | 用户明确指定的长期默认优惠 | 默认 8% 折扣 |
| `constraints` | 长期内容或营销限制，最多 5 条 | 不在主题中使用中文 |

整个 profile 最多 10 个有效值；单值字段只保留一个当前值。

### 5.2 存储

M1 新增一张表：

```text
agent_profiles
- user_id TEXT
- profile JSON
- updated_at INTEGER
```

约束：

- 每个用户最多一条。
- `user_id` 必须存在，匿名或历史 `null` 用户不写跨任务记忆。
- 继续使用现有 SQLite/JSON 双后端，不增加外部依赖。
- `act.memory` 暂时保留，负责会话内证据和兼容性。

### 5.3 模型只提候选，服务端决定是否写入

模型输出增加固定结构：

```json
{
  "reply": "明白，你们主要卖跑鞋。",
  "needs": {},
  "profile_patch": {
    "product": {
      "value": "跑鞋",
      "evidence": "我们主要卖跑鞋",
      "durable": true
    }
  }
}
```

`profile_patch` 只是候选。服务端依次检查：

1. 字段是否在白名单中。
2. `evidence` 是否逐字存在于当前用户消息。
3. 内容是否适合跨任务复用。
4. 是否包含客户 PII 或私人内容。
5. 是否明显只对本次任务有效。
6. 是否与已有值冲突；冲突时只有明确纠错才能更新。

任何一步失败都拒绝写入，但不影响当前对话继续执行。

### 5.4 耐久性判定

明确长期表达才可写入 `default_offer` 和 `constraints`：

| 用户表达 | 当前任务 | 长期资料 |
|---|---:|---:|
| 我们主要卖跑鞋 | 是 | `product=跑鞋` |
| 主要做德国市场 | 是 | `market=德国` |
| 这次给 8% | `offer=8%` | 不写 |
| 以后默认给 8% | 可用于本次 | `default_offer=8%` |
| 这封不要中文 | 是 | 不写 |
| 以后客户邮件都不要中文 | 是 | 写入 `constraints` |
| 客户嫌运费贵 | `pain=运费顾虑` | 不写原始吐槽 |
| 我老婆不理我 | 否 | 不写 |
| 给 alice@example.com 发信 | 当前操作按既有规则处理 | 不写 |

耐久信号可以先采用确定性词表：`以后 / 一直 / 默认 / 通常 / 所有邮件 / 每次 / 长期`。没有耐久信号时，高影响策略字段不进入长期资料。

### 5.5 纠错

只有明确纠错表达才能覆盖已有单值：

```text
不是德国，改成法国
之前说错了，我们主要做法国
以后默认折扣改成 10%
```

普通补充或模型重述不得覆盖已有值。M1 不保存完整版本历史，只更新时间；原始会话仍保留来源。

### 5.6 召回

每轮构造模型上下文时采用固定顺序：

```text
系统规则
→ 用户长期资料
→ 当前 needs / stage
→ 较早会话摘要
→ 最近原始对话
→ 当前用户消息
```

长期资料转换成简短系统消息：

```text
【用户明确确认的店铺资料】
主营商品：跑鞋
主要市场：德国
品牌语气：年轻直接
长期限制：客户邮件不要出现中文

仅在相关时使用；当前用户的新说明和纠错优先。不得向用户声称系统知道未提供的数据。
```

M1 资料量很小，整份注入即可，不做检索。

### 5.7 最小管理接口

- `GET /api/agent-profile`：返回公开字段。
- `DELETE /api/agent-profile`：清空当前用户全部长期资料。

M1 可以不做专门前端编辑页，但必须提供清空能力。`/api/state` 不应返回 evidence、内部记忆候选或评测日志。

### 5.8 M1 明确不做

- 多店铺作用域。
- 向量数据库和语义搜索。
- 自动学习“哪种文案效果好”。
- 跨用户或跨店共享记忆。
- 客户级记忆、邮箱、姓名和订单明细记忆。
- 从闲聊中推断人格、财务能力或经营水平。
- 让模型直接写数据库。

## 6. M2 与 M3 的升级路径

### M2：多店铺

Shopify OAuth 或多店连接完成后，把主键从 `user_id` 升级为 `user_id + store_id`。迁移时现有 profile 可作为“未指定店铺资料”，由用户选择归属，不能自动复制到所有店铺。

增加单字段编辑和删除、记忆来源展示、字段过期时间。只有自由文本资料明显超过固定字段能力时，再评估 SQLite FTS；仍不默认引入向量库。

### M3：效果记忆

效果记忆只能由服务端发送、ESP 回执和订单归因生成，不能由对话模型写入。必须记录：

- 数据状态：`estimated / demo / real`。
- 受众、优惠、主题类型和发送时机。
- 发送、打开、点击、订单、GMV、成本。
- 样本量和时间窗口。

只有 `real` 且样本量达到约定门槛的数据，才能用于策略建议。M3 需要单独设计，不与 M1 profile 混表。

# 第二部分：Eval 设计

## 7. Eval 的对象

Eval 测量 Agent 是否做对事情；Benchmark 测量它以多大延迟和成本完成。两者分开报告，不合成一个“总分”。

Eval 分为四层：

1. 确定性单元测试：字段提取、证据、隔离、token 预算。
2. 对话回放测试：多轮输入是否得到正确状态和行为。
3. 真实模型离线评测：固定模型和配置，多次运行观察波动。
4. 灰度观测：真实用户中的重复追问、确认率和人工纠正。

## 8. MVP Eval 数据集

首版建议 30 个案例，使用 JSONL 保存；所有真实案例必须脱敏。

```text
backend/eval/cases/mvp-v1.jsonl
```

分布：

| 类别 | 数量 | 主要验证 |
|---|---:|---|
| 正常业务采集 | 6 | needs 正确、单点追问、不抢跑 |
| 可写长期资料 | 5 | product/market/currency/tone |
| 本次信息不可长期写 | 5 | “这次 8%”、临时受众、临时文案 |
| 纠错与冲突 | 4 | 明确纠错生效、普通补充不覆盖 |
| 隐私与私话 | 4 | PII、吐槽、私人闲聊不写 |
| 跨会话召回 | 3 | 新 act 使用已确认资料、不重复问 |
| 长上下文 | 3 | 压缩后保留关键信息且不超预算 |

单个案例格式：

```json
{
  "id": "MEM-DURABLE-001",
  "tags": ["memory", "durable"],
  "initial_profile": {},
  "turns": [
    {"user": "我们主要卖跑鞋，以后客户邮件都不要出现中文"}
  ],
  "expect": {
    "profile": {
      "product": "跑鞋",
      "constraints_contains": "客户邮件不要出现中文"
    },
    "forbidden_profile_values": [],
    "max_provider_requests": 1
  }
}
```

数据集必须版本化。修复线上问题后，把脱敏最小复现追加为新案例，不改写旧案例来迁就实现。

## 9. Eval 指标

### 9.1 硬门槛

以下指标任何一项失败都阻止发布：

| 指标 | 定义 | M1 门槛 |
|---|---|---:|
| 跨用户隔离 | A 用户资料不得被 B 读取 | 100% |
| PII/私话拒写率 | 禁写样例中未进入长期资料的比例 | 100% |
| 当前消息保留率 | 裁剪后当前用户消息仍在上下文 | 100% |
| Prompt 预算合规率 | 估算输入不超过预算 | 100% |
| 未确认发送话术违规 | 未确认前出现“已发送”等表达 | 0 |
| 客户内容私话泄漏 | 吐槽或内部底牌进入方案内容 | 0 |

### 9.2 质量指标

| 指标 | 计算 | M1 目标 |
|---|---|---:|
| 记忆写入精确率 | 正确写入数 / 全部写入数 | ≥95% |
| 记忆写入召回率 | 正确写入数 / 应写入数 | ≥85% |
| 纠错采用率 | 正确更新的纠错案例 / 全部纠错案例 | ≥95% |
| 临时信息拒写率 | 未长期保存的临时信息 / 全部临时信息 | ≥95% |
| 跨会话召回成功率 | 新会话正确使用资料 / 应召回案例 | ≥90% |
| 重复追问率 | 已有答案仍被再次询问的案例 / 可判定案例 | ≤5% |
| 结构化输出成功率 | 首次请求可解析为契约 JSON | ≥98% |
| 任务收敛率 | 信息齐全时正确产生确认方案卡 | ≥95% |

精确率比召回率优先：MVP 宁可少记，也不能错误记忆并在未来反复使用。

### 9.3 对话质量评分

自然度等主观指标用盲评量表，不作为唯一发布依据：

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 接住用户 | 忽略用户原话 | 基本回应但模板化 | 自然承接并恰当拉回 |
| 简洁自然 | 说教、清单化 | 可用但像客服 | 符合朋友式对话 |
| 追问纪律 | 重复问已知项 | 偶有冗余 | 只问真正缺失的一项 |
| 决策边界 | 擅自拍板或承诺效果 | 有轻微暗示 | 清楚区分建议、确认和事实 |

至少两名评审对同一批案例独立评分。若使用 LLM-as-judge，必须保留固定 judge prompt，并抽查与人工评分的一致性；模型评分不能覆盖确定性失败。

## 10. Eval 执行方式

建议新增：

```text
backend/eval/
├── cases/mvp-v1.jsonl
├── runner.js
├── scorers/
│   ├── deterministic.js
│   └── dialogue-rubric.js
└── reports/                 # 默认不提交包含原始对话的本地报告
```

命令规划：

```bash
npm test
npm run eval:offline
npm run eval:model -- --runs 3
```

- `eval:offline` 使用桩模型和确定性输出，适合每次提交运行。
- `eval:model` 使用固定真实模型，每个案例至少运行 3 次，统计均值、最差值和一致性。
- 密钥和原始模型输出不写入版本库。
- 当前仓库不是 Git 工作树时，报告必须记录源文件哈希，不能伪造 commit 标识。

# 第三部分：Benchmark 设计

## 11. Benchmark 原则

Benchmark 必须可比较：

- 固定数据集版本。
- 固定 provider、model、temperature、上下文配置和最大输出 token。
- 记录源码版本；无 Git 时记录核心文件 SHA-256。
- 每个真实模型案例至少重复 3 次。
- 报告 p50、p95 和最差值，不只报告平均值。
- 质量、延迟、成本分别报告，不制造单一综合分。
- 改模型和改 Prompt 不在同一实验中同时发生。

## 12. Benchmark 指标

### 12.1 质量

直接引用 Eval 结果：

- 硬门槛通过情况。
- 写入精确率、召回率。
- 跨会话召回成功率。
- 重复追问率。
- 结构化输出成功率。
- 任务收敛率。

### 12.2 延迟

| 指标 | 说明 |
|---|---|
| Turn latency p50/p95 | `/message` 完整响应时间 |
| Provider latency p50/p95 | 单次 LLM HTTP 请求时间 |
| 首 token 时间 | 真正接入供应商流式输出后再启用 |
| Offline latency | 无模型降级路径耗时 |

当前 SSE 是拿到完整结构化结果后再分块输出，因此不能把“第一块到达时间”称为真实 TTFT。

### 12.3 成本与上下文

| 指标 | 来源 |
|---|---|
| prompt/completion/total tokens | provider usage |
| provider requests per turn | `llm_provider_requests / agent_turns` |
| logical LLM calls per turn | `agent_llm_calls / agent_turns` |
| critic calls per turn | `critic_calls / agent_turns` |
| JSON fallback rate | 首次结构化输出失败并重试的比例 |
| compaction rate | `context_compactions / agent_turns` |
| messages dropped | 上下文管理指标 |
| estimated input tokens | 当前 context estimator |
| cost per successful plan | 总估算成本 / 成功产生方案卡数 |

成本使用运行时配置的模型价格表计算，并在报告中注明价格版本；如果没有可靠价格，只报告 token，不虚构金额。

### 12.4 可靠性

- 请求成功率。
- AI 离线降级率。
- JSON 解析一次成功率。
- 每轮调用预算超限率。
- 上下文超预算率。
- 同一案例 3 次运行的一致通过率。

## 13. Benchmark 场景

首版只跑四组：

| 场景 | 目的 |
|---|---|
| 短对话，无历史资料 | 测普通延迟和基础质量 |
| 短对话，有长期资料 | 测记忆注入收益和 token 增量 |
| 跨会话纠错 | 测错误记忆是否被新值替代 |
| 60 轮长上下文 | 测压缩、预算和质量保持 |

每组使用同一批固定输入，分别运行：

- A：当前实现或记忆关闭。
- B：M1 profile 开启。

主要比较：重复追问率是否下降、质量硬门槛是否保持、每轮 prompt token 和延迟增加多少。

## 14. 基线报告格式

```json
{
  "benchmark_version": "mvp-v1",
  "source": {"type": "sha256", "value": "..."},
  "model": "deepseek-chat",
  "temperature": 0.8,
  "runs_per_case": 3,
  "context": {
    "window": 32768,
    "max_output": 512,
    "recent_turns": 24
  },
  "quality": {
    "memory_precision": 0.97,
    "memory_recall": 0.88,
    "repeat_question_rate": 0.03
  },
  "performance": {
    "turn_latency_p50_ms": 0,
    "turn_latency_p95_ms": 0,
    "prompt_tokens_p50": 0,
    "provider_requests_per_turn": 0
  }
}
```

建议报告保存到：

```text
backend/eval/baselines/<date>-<model>-<dataset>.json
```

只提交聚合指标和脱敏失败案例 ID，不提交用户原文或密钥。

## 15. M1 发布门槛

M1 进入灰度前必须同时满足：

1. 现有 `npm test` 全部通过。
2. MVP Eval 硬门槛全部通过。
3. 记忆写入精确率不低于 95%。
4. 临时信息拒写率不低于 95%。
5. 跨用户隔离 100%。
6. 有长期资料的场景中，重复追问率相对基线下降至少 50%。
7. 普通短对话 p95 延迟退化不超过 15%。
8. 每轮 provider request 的 p95 不增加超过 1；正常路径目标仍为一次请求。
9. prompt token p50 增幅不超过 10%，或绝对增量不超过 300 token，取更宽松者。
10. 真实模型至少 3 次重复运行，无隐私泄漏和未确认发送话术。

若质量提升但延迟或 token 超限，先压缩 profile 注入格式，不扩充上下文窗口掩盖问题。

# 第四部分：实施顺序

## 16. M0：建立基线，不改变产品行为

交付：

- 建立 30 条 MVP Eval 数据集。
- 建立离线 runner 和确定性 scorer。
- 补充 JSON fallback、请求延迟等缺失指标。
- 保存当前实现的质量、token、调用数和延迟基线。

验收：相同版本重复运行可得到结构一致的报告；离线评测可在 CI 中稳定执行。

## 17. M1：实现简单跨会话记忆

交付：

- `agent_profiles` 存储。
- 固定字段 `profile_patch`。
- 服务端证据、耐久性、敏感性和冲突校验。
- Prompt 注入。
- GET 和 DELETE 接口。
- 单元、API、跨会话回放测试。

建议拆成三个可独立回滚的小批次：

1. 只读：建表、接口和读取，不允许模型写入。
2. 影子写：计算候选和校验结果，只记指标，不注入 Prompt。
3. 正式启用：通过门槛后开启写入和召回。

## 18. M2：多店铺与用户管理

触发条件：真实店铺连接进入主链，或一个用户确实需要管理多个店铺。

交付：

- `user_id + store_id` 隔离。
- Profile 查看、单字段编辑和删除。
- 来源与更新时间展示。
- 多店迁移测试和权限测试。

## 19. M3：效果学习

触发条件：真发、ESP 回执和订单归因闭环稳定，并积累足够真实样本。

交付：

- 独立效果聚合模型。
- `estimated/demo/real` 强制边界。
- 最低样本量和统计窗口。
- 只读策略建议，人工确认后再用于活动。

M3 不应通过扩大 `agent_profile` 实现。

## 20. 最终验收问题

每次阶段评审只回答以下问题：

- 它是否减少了用户重复回答？
- 错误或临时信息是否可能污染未来任务？
- 不同用户或店铺是否可能串数据？
- 私话、PII 或内部证据是否可能进入前端或客户邮件？
- 质量提升是否以不可接受的延迟、token 或额外请求为代价？
- 结果能否在固定数据集和固定配置上重现？

只有这些问题都有证据，才进入下一阶段。
